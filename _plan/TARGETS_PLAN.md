## 0. Цель владельца (как я её понял)

1. **Мир без границ.** Пешки уходят далеко (17.Б, «хоть 200 к»), за кромкой **строят руками, пешком** (24.Б), всё это **сохраняется в стриминговые чанки** (25.А).
2. **Честная симуляция.** Стройка ждёт 100 % материалов, но **без иконок** — недостача видна **в информации о зоне** (1.Б, 7). Зоны без назначенных людей **не работают** (18.Б). Срывы **активные** (9.Б), смерть — **кома, а не мгновенная смерть** (8.Б).
3. **Глубокое производство.** Авто-крафт (6.А) + «подробно продумать производство» (П-1…П-4), полноценное окно верстака (8.Б).
4. **Производительность и масштаб.** O(K)-диспатч (19.А), монолитные прямоугольники вместо 250k линий (20.А), LOD чертежей (22.А), тени под предметы (23.А), сдвиги вместо делений (16.А).
5. **Интерфейс.** Инспектор жителя (13.А), «почему нельзя» у курсора + красный чертёж (14), подтверждение сноса зоны (UI-14), ошибки размещения (15.А).

## 1. Принципы (как решаю)

1. **Минимальная правка под цель.** Одна правка — один смысл. После каждой — `dotnet build Game.csproj` = 0/0.
2. **Порядок потери ценности:** сначала «цель не работает вовсе» → потом «работает плохо» → потом полировка.
3. **Не переписывать живое ради NextGen.** Лабораторный код (`_test_*`) — источник идей, не каркас. Мёртвые домены из `src/` убираем.
4. **Дерево правится параллельно:** перед правкой перечитывать участок по цитате (не по номеру строки), один владелец — один файл.
5. **Перестройка — только через вопрос владельцу**, не «по-тихому».

### Фаза P — сверхоптимизированный A* (решения владельца приняты)

Планка: **локальный путь ≤3 мкс; дальний 20–60 мкс; тёплый (кэш) ~200–400 нс; 10k дальних холодных ≤300 мс на 4 потоках; 10k к общим целям 2–8 мс.** «0.1 мс на 10k путей» физически невозможно (10 нс/путь при DRAM 60–100 нс) — к этой цифре подходим только тёплым кэшем/oracle-эмуляцией.

**Бюджет кадра — 16,6 мс (60 FPS).** Отсюда жёсткие лимиты на pathfinding:
- **Главный поток (UI/инструменты/призраки): ≤0,5 мс на кадр.** Наведение мыши не имеет права звать A* — только raycast/steering. Дальше — в очередь.
- **Sim-поток (агенты): слайс ≤2,0 мс за суб-степ**, с очередью по приоритету (сначала пути для уже назначенных работ, потом «просто хочу пройти»).
- **Пик 10 000 путей** не обрабатывается в одном кадре: только через кэш/flow-fields (тёплый путь ~0,3 мкс ⇒ 10k ≈ 3 мс суммарно / 0,75 мс на 4 потоках) или через размазывание по кадрам (≤2 мс/кадр). Холодный шторм 10k × 48 мкс = 480 мс — недопустим, поэтому кэш/HPA* обязательны, а не «опциональны».
- Если бюджет исчерпан — путь **откладывается** (агент продолжает текущий waypoint), а не ищется «прямо сейчас». Метрика в F3: поисков/кадр, мс/кадр, отложено, кэш-хиты.

### P3.2 — математическое улучшение тёплого пути (2026-11-09): кэш ЦЕЛОГО маршрута

По-хоповый кэш (113 словарных проб на путь) заменён на **кэш целого маршрута**: ключ (чанк старта → чанк цели) → сжатая последовательность порталов + версия мира. Промах/попадание проверяются одной пробой словаря; запись инвалидируется версией при любом изменении проходимости.

| Режим | Было (по-хоповый) | Стало (целый маршрут) |
|---|---|---|
| тёплый путь (avg 7 249 тайлов) | 85 мкс | **6,9 мкс (p50 4,8)** |
| 10 000 тёплых путей, 1 поток | ~850 мс | **~69 мс** |
| то же на 4 потоках | ~210 мс | **~17 мс** |
| полухолодный (новый чанк цели) | — | ~1,09 мс (p50 0,81) |
| холодный (постройка графа) | — | 75 мс разово |

Следующие математические шаги (полухолодный — это A* по порталам, ~673 раскрытия):
1. **Bidirectional A*** (вперёд от стартовых порталов, назад от целевых) — математически √-сокращение раскрытий (~2×).
2. **Goal-directed эвристика**: h = min по целевым порталам (октиль до портала + точный tailcost) — сокращает раскрытия на 20–40 %.
3. **Tie-break по большему g** при равном f — ещё 10–20 %.
4. **Контракция 2-портальных чанков** (вход=выход) — на открытой местности убирает большинство узлов.

### P3.3 — СДЕЛАНО (goal-directed эвристика) + честный результат по weighted A*

Реализована допустимая goal-directed эвристика: `h(n) = min_p (octile(n → портал p) + tail(p))`, где `tail(p)` — **точная** стоимость от целевого портала до цели (считается один раз на запрос).

| Режим (avg 7 249 тайлов) | До эвристики | После |
|---|---|---|
| полухолодный путь | 1 089 мкс (p50 810) | **807–846 мкс (p50 ~780)** |
| expansions | 673 | **635** |
| тёплый (кэш маршрута) | 6,9 мкс | 7,2–7,5 мкс (без изменений) |
| корректность | 60/60, ratio 1,09 | 60/60, ratio 1,10, waypoints на проходимых 0 |

**Weighted A\* (ε=1.25) — ОТВЕРГНУТ по замеру:** avg 9,3 мс, p50 3,1 мс — в 10× хуже базового. Причина: при недопустимой эвристике закрытые узлы требуют переоткрытия, которого в текущей реализации нет, поиск упирается в кап раскрытий. `HeuristicWeight` оставлен свойством со значением 1.0 (оптимальный режим).

Осталось из математики: **bidirectional A\*** (самый крупный резерв, ~2×) и **контракция 2-портальных чанков**; плюс P5-бюджет.

### P3.4 — СДЕЛАНО: жадный incumbent + pruning (2026-11-09)

Добавлен **жадный маршрут-верхняя-граница** перед A*: на каждом чанке выбирается прогон
`min(стоимость дойти + октиль до цели)`. Он даёт incumbent `bestTotal`, после чего `Expand`
отсекает ветви, чья оптимистичная оценка уже хуже incumbent. Если A* не нашёл строго лучше —
возвращается жадный маршрут, и он **кэшируется** (иначе тёплый проход для таких пар пересчитывался бы).

| Метрика (avg 7 249 тайлов) | P3.3 | P3.4 |
|---|---|---|
| expansions на путь | 635 | **444 (−30 %)** |
| полухолодный путь | 807–846 мкс | **~805 мкс (p50 841, p95 1,8 мс)** |
| тёплый путь | 7,2 мкс | **6,4 мкс (p50 4,3)** |
| waypoints | 213 | **181** |
| 10 000 тёплых путей | ~72 мс | **~64 мс (1 поток) / ~16 мс (4 потока)** |
| корректность | 60/60, ratio 1,10 | 60/60, ratio 1,35* |

\* ratio 1,35 — это отношение «длина по waypoint-ам / прямая»; часть путей отдаётся жадным fallback'ом
(когда A* не строго лучше), который может быть на 20–30 % длиннее оптимума. Для геймплея приемлемо,
но если нужна оптимальность — следующий шаг: bidirectional A* + контракция чанков (убирают и fallback,
и хвост p95).

### P3.5 — ИСПРАВЛЕНЫ ДВА БАГА КУЧИ (2026-11-09)

1. **Упаковка ключа кучи ломалась при id ≥ 4096.** Было `(uint)(f << 12) | (uint)node` — у нас 36 475 порталов,
   так что старшие биты id наезжали на `f`, и `PopOpen` возвращал чужой узел. Стало: 64-битный ключ
   `((long)(f * 1024 + min(1023, h>>8)) << 32) | (uint)node` (tie-break: при равном f раскрываем глубже, т.е. меньшую h).
2. **Ранний выход при `f >= bestTotal`** не давал дойти до корректного пути равной стоимости и отдавал жадный
   fallback. Заменено на строгое `f > bestTotal`.

### P5 — СДЕЛАНО (2026-11-09): бюджет поиска пути на суб-степ

`AgentMovementService`:
- `BeginPathBudgetStep()` вызывается из сим-потока на **каждом суб-степе** (сброс счётчика).
- Поиск пути обёрнут в замер; потраченное время аккумулируется в `PathBudgetSpentMs`.
- Если бюджет `PathBudgetMs = 2.0` исчерпан — путь **не ищется сейчас**: агент получает кулдаун 0.05 с (≈1 кадр) и продолжает идти по текущим waypoint-ам; счётчик `PathBudgetDeferred` показывает, сколько запросов отложено.
- Тем самым пик «10 000 агентов одновременно просят путь» размазывается по кадрам вместо одного фриза: худший случай на кадр ≤2 мс поиска (12 % бюджета 16,6 мс), остальное — рендер/UI/симуляция.

Проверка: сборка 0/0; статически — единственная точка входа `RequestHierarchicalPath` под бюджетом; путь деградирует в «подождать кадр», а не в «идти напрямую сквозь стену».
