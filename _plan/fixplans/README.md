# Планы минимальных правок — волна 2026-11-07

Цель: для каждого открытого бага из `_plan/BUGS_REGISTRY.md` (§13–§17) дать **минимальную правку**, которую можно отдать другому ИИ-агенту как задачу.

## Формат каждой карточки (обязателен)

```
### <ID> · <P> · <короткий заголовок>
- **Файлы:** `путь/файл.cs:СТРОКА` (и соседние, если правка затрагивает 2 файла)
- **Минимальная правка:** конкретно что менять. Для кода — блок «было → стало» (или точное описание в 1–3 предложениях, если меняется одна строка/условие).
- **Что НЕ трогаем:** границы правки (какие файлы/подсистемы намеренно не задействованы).
- **Риск:** что может сломаться и почему это приемлемо (или как откатить).
- **Проверка:** как убедиться, что баг закрыт (существующий тест / новый стенд / сценарий в игре).
- **Объём:** S (≤10 строк) / M (10–50) / L (>50 или несколько файлов).
- **Перестройка:** «нет» либо **ТРЕБУЕТ РЕШЕНИЯ ВЛАДЕЛЬЦА** + вопрос в 1–3 строки + 2–3 варианта с плюсами/минусами.
```

## Правила

1. **Минимальность:** правка не должна переписывать архитектуру. Если без перестройки не обойтись — не выдумываем, а помечаем «ТРЕБУЕТ РЕШЕНИЯ ВЛАДЕЛЬЦА» и даём варианты.
2. **Один баг — одна правка.** Если две карточки лечатся одной правкой — указать это явно («закрывает также …»).
3. **Никаких правок кода в этой волне:** только план. Код (`src/`, `scenes/`, `tests/`, `project.godot`) read-only; git не трогать; Godot/`dotnet build` не запускать.
4. **Доказательность:** каждая правка опирается на прочитанный код (`файл:строка` + цитата), а не на догадки. Если строка «уехала» — найти актуальную.
5. **Проверяемость:** у каждой правки — конкретный способ проверки. Если есть тест в `tests/` — назвать файл; если нет — описать минимальный стенд.
6. **Порядок применения:** в конце файла — «волны»: что применять первым (зависимости между правками), что можно параллельно.
