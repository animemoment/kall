# МНОГОАГЕНТНАЯ СИСТЕМА ПРОЕКТА (GODOT 4.7 C#)

В этом проекте действует разделение обязанностей между 4 специализированными субагентами. Главная модель должна координировать их работу и переключаться между ролями в зависимости от этапа задачи.

## 1. Агент-Архитектор (@architect)
- **Цель**: Анализ ТЗ, проектирование структуры и контроль соответствия кода бизнес-логике.
- **Инструкция**: Изучи проект. Прежде чем писать код, сформируй или обнови в корне репозитория файл `PLAN.md`. Распиши в нем интерфейсы классов, методы и архитектуру. Если алгоритм сложный — сначала отправь задачу агенту `@researcher`.

## 2. Агент-Поиск (@researcher)
- **Цель**: Поиск актуальных библиотек, паттернов оптимизации и лучших практик для C# в Godot 4.7.
- **Инструкция**: Используй инструмент веб-поиска (websearch). Ищи информацию по оптимизации C# (минимизация GC pressure, пулы потоков, Compute Shaders). Выдавай структурированный отчет Архитектору. Код проекта не меняй.

## 3. Агент-Работник (@developer)
- **Цель**: Написание чистого, рабочего C# кода.
- **Инструкция**: Пиши и редактируй файлы строго в папке `src/` на основе составленного файла `PLAN.md`. Твоя цель — эффективная симуляция без утечек памяти. Если `@destroyer` нашел баг — хладнокровно исправляй код.

## 4. Агент-Разрушитель (@destroyer)
- **Цель**: Состязательное тестирование (Adversarial Testing). Поиск уязвимостей и крайних случаев.
- **Инструкция**: Тебе КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО напрямую изменять игровой код в папке `src/` или сцены в `scenes/`. Ты создаешь mock-данные и тест-сценарии (например, файлы `bad_data.json` с некорректными или null-значениями). Передавай описание ситуаций отказа Работнику в формате: `@developer, если симуляция получит такие данные, всё упадет с NullReferenceException. Исправляй`.

# ПРАВИЛА ПРОИЗВОДСТВЕННОЙ ЭКОНОМИКИ (обязательны для всех ролей)

Сеттинг: **1920–1930-е**, экономика приближена к реальной. Эти четыре правила — закон.
Любой новый рецепт, товар или рабочее место проверяется по ним. Нарушил — переделывай.

## П-1. Правило отсечения: шаг остаётся, только если создаёт выбор или узкое место

Промежуточный этап живёт, если он:
- даёт **развилку** (из него идут ≥2 разных продолжения), или
- является **узким местом** (его нехватка останавливает всю ветку).

Шаг, который просто «ещё одна переработка» без развилки, — **удаляется**.
Примеры: агломерат/окатыши перед домной — убрать; штейн перед медью — слить;
лигроин и уайт-спирит — убрать; обои и газета — слить в «бумага/картон».

## П-2. Промтовар участвует в производстве промтовара

Запрещено проектировать дерево как «сырьё → товар → склад». Конечные товары
обязаны быть связаны между собой **двумя механизмами**:

1. **Расходуемый компонент** — товар физически входит в изделие и исчезает
   (лист → корпус, стекло → окно, резина → шина).
2. **Оборудование рабочего места** — товар НЕ расходуется, но без него рабочее
   место не работает (токарный станок нужен, чтобы точить вал; вакуумный насос —
   чтобы делать лампы; прокатный стан — чтобы получить лист).

Следствие: **капитальные товары (станки, двигатели, насосы) — это входы
производства, а не украшение склада.** Именно они образуют прогрессию.

## П-3. Сложное изделие не может быть простым

Двигатель, лампа, радио, станок, трактор — это **не «сталь + чугун»**.
Сложное изделие собирается из узлов, каждый узел — из компонентов, каждый
компонент — из материалов. Глубина — 3–4 уровня сборки.

Пример-эталон: **лампа накаливания** — 5 доменов (стекло, металлургия, химия,
энергетика, машиностроение), 4 единицы оборудования, 6 переделов только на нить
(вольфрамит → кислота → порошок → спекание → волочение через алмазные фильеры).

## П-4. Формальный критерий глубины

**Сложное изделие (T5) проходит, только если у него:**
- ≥ **3 разных домена** (не только металл);
- ≥ **2 передела** внутри каждого домена;
- ≥ **1 единица оборудования**, без которой цех не работает;
- ≥ **1 химический компонент**;
- ≥ **5 различных входов** на финальной сборке.

**Простое изделие** (гвоздь, доска, кирпич) — 1 домен, 1 передел. Это нормально:
это массовый товар, а не машина.

**Следствие для геймплея:** глубина = площадь = инвестиции. Каждый передел — это
рабочее место, рабочее место — клетки в коробке. Моторный цех не может быть
сараем 3×3: не хватит места под литьё и пять станков. Тип здания определяется
**не названием, а составом рабочих мест внутри**.

**Запрещённый антипример:** «двигатель = сталь + чугун», 1 домен, 0 оборудования,
2 входа → **не проходит П-4**, переделать.

## 5. Реальные каталоги проекта

| Каталог | Что внутри | Кто правит |
|---|---|---|
| `src/` | игровой C#-код — источник истины по поведению | @developer |
| `scenes/`, `ui/`, `assets/` | сцены, UI-ресурсы, текстуры | @developer (сцены — осторожно) |
| `docs/` | ADR `DECISIONS.md`, `ARCHITECTURE.md`, аудиты API (`WorldDeltaApiAudit.md`, `MapDataWriterAudit.md`), `LIVE_BRIDGE.md` | все роли, по одной правке за раз |
| `_plan/` | план и реестры: `BUGS_REGISTRY.md`, `DEFECTS_MASTER.md`, `REGRESSIONS.md`, `00_MASTER_PLAN.md`, тематические планы (`R_render_perf.md`, `W_world_streaming.md`, `J_jobs_agents.md`) | @architect |
| `_audit/` | снимки инструментов аудита (циклы, зависимости) — только чтение | никто (артефакты) |
| `_reports/` | отчёты по задачам и скриншоты прогонов | исполнитель задачи |
| `tests/` | тесты и стенды; **исключены из сборки** (`<Compile Remove="tests/**" />` в `Game.csproj`) | @destroyer |

## 6. Сборка и запуск движка (жёсткое правило §119 `PLAN.md`)

- **`dotnet build Game.csproj` = 0 ошибок после каждой правки** — единственная разрешённая агентам сборка.
- **Godot агенты напрямую не запускают.** Допустимый путь один — `godot_run_headless --script tests/run_*.gd`;
  прямой запуск `Godot_v4.7-stable_mono_win64.exe` из pwsh/bash даёт signal 11.
- Запуск игры с окном — действие человека, а не агента.

## 7. Запреты

- Не удалять файлы, не трогать `git`.
- Не исполнять списки-кандидаты из `_plan/` как задачи: они требуют отдельного решения владельца.
- Правила производственной экономики (П-1…П-4) обязательны для любого нового рецепта, товара и рабочего места.
